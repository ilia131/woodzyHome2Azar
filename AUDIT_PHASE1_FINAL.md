# HomeAksoria Phase 1 final technical audit

## 1. Executive summary

**Readiness: READY AFTER FIXES.** The tested PostgreSQL checkout, cancellation and expiration paths serialize competing stock changes and roll back failed writes. The baseline was independently reproduced: **94 tests passed**. The local Compose runtime uses a PostgreSQL superuser for application processes, and a legacy absolute stock write can apply a stale inventory count after a successful reservation. Resolve these before production or before treating physical stock correctness as established across every entry point. Payment development should follow an approved transaction and late-payment design. No payment endpoint or provider was exercised.

Evidence labels used below: **verified issue** means visible directly in the implementation, observed configuration or read-only command output. Reproduction steps describe how to demonstrate the identified behavior, even where this audit did not execute the steps. **Potential risk** is inferred and unverified by a matching test. **Not tested** and **not applicable** are explicit evidence limits. Severity is independent of the label.

Reviewed stock writers in `products/{models,admin,admin_api}.py`, audit and role provisioning in `core/{models,admin_api,audit_api}.py` and `core/management/commands/provision_roles.py`, JWT account state checks, order/core migrations, test sources, Celery settings, Compose, gateway and environment template. The audit did not update application source, fixtures, persistent configuration, roles, or application database records.

## 8. Security findings

Address/cart/order endpoints use `PrivateCommerceAPI`, `IsAuthenticated`, owner selectors or service filters, and `no-store`. The checkout serializer accepts a bounded positive address ID and rejects extra keys. Order and item outputs omit internal reservation data and account IDs on owner routes. Admin order output includes shipping PII intentionally for staff with `orders.view_order`; access retention, export policy and privacy review were not assessed. Cancellation has the revocation timing risk M6. Logging review found structured actor/object audit data and safe checkout metadata. Unexpected database exceptions can include database detail in logs, so PII redaction and log routing require production review. No intrusive security testing was performed.

Observed live settings are a loopback HTTP profile. `check --deploy` returned `security.W004`, `W008`, `W012`, `W016` for HSTS, redirect and secure cookies. This is verified local-profile behavior. Before external access, validate real TLS termination, proxy headers, secure cookies, trusted origins and secrets rotation with the actual production deployment. This is covered by configuration inspection only.

## 9. Inventory accounting findings

Available is `Product.stock`; held is the sum of active reservation quantities; consumed is tracked by consumed reservations and zero-delta consume movements. Expired active records can remain deducted until reconciliation commits. Under the service, reconciliation is opening available balance plus the sum of `available_delta`, with terminal movement uniqueness preventing a second restoration. The read-only live aggregate reported zero discrepancies on **zero products and zero movements**; this is not evidence of successful reconciliation with data. Ordinary application API writes route through inventory services; Django admin copies locked stock on edit and records initial balance on creation. The backward-compatible absolute path and offline ORM bypass are H1 and M2. No separate counting/synchronization of warehouse on-hand stock exists.

## 10. Concurrency findings

Checkout uses account → products ordered by ID, then commits new order/holds and stock. Cancellation, expiry and internal consumption use order → active reservations → products ordered by ID. The cart and address API uses account locks, while cart availability writes additionally take a product lock. Checkout's expiry sweep runs before its main atomic block; it can commit overdue releases independently of a failed new checkout. This is intentional and distinct from the new order's atomic guarantees. The inspected code does not use an `on_commit()` callback to mutate stock. Small integration tests cover reverse product order, the final unit, same-cart requests, and two workers/cancellation. They do not prove deadlock freedom in all admin, maintenance or future payment paths. Do not perform slow external work inside order/product lock scopes.

## 11. Order lifecycle findings

The exposed transitions are pending → cancelled and pending → expired. Expiry may release an overdue active hold on a non-pending order without changing that order's status; the existing test deliberately exercises this behavior. No API sets paid, processing or completed. Internal consumption refuses non-pending orders, incomplete holds or expired holds, and never marks the order paid itself. These are currently separate concerns and must commit together in a future payment path. The historical image and deadline presentation caveats are L1 and M3. The audit did not create or simulate paid orders beyond the existing automated fixtures.

## 12. Database and migration findings

All migrations were applied; no model drift. Read-only PostgreSQL catalog queries confirmed stock non-negativity, unique cart owner/product, positive quantity, order arithmetic constraints, unique reservation item, reservation status/timing constraints, unique operation key, unique reserve and terminal movement indexes, and the unique default-per-account partial index. Orders protect users from deletion; shipping addresses and historical product FKs can be null. Active reservation state requires a product; linked movement records retain original product ID even when the current product is removed. The opening balance migration is additive and leaves legacy orders without inferred reservations. A production-size upgrade from a populated legacy database and accounting lineage were not tested. See M2 for consistency beyond row-local constraints.

## 13. Performance findings

Order retrieval prefetches items; admin retrieval prefetches items and reservations; cart joins product and uses a visibility subquery. A classic per-row serializer N+1 was not found on those paths. Per-line inventory writes are synchronous and do scale with line count. Read-only `EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)` used `reservations_due_idx` followed by sort/unique for the due query and `orders_user_latest_idx` for owner order listing. Both returned zero rows; observed execution times were 0.041 ms and 0.029 ms respectively and are not capacity measures. Test with representative product fanout, due-order backlog, queue latency, interleaved adjustments and checkout, and quantify p95/p99 and lock waits before sizing production.

## 14. Docker and deployment findings

Existing Compose services were observed without restart or recreation. DB, Redis and web reported healthy; gateway, worker and Beat were up; one-shot init exited 0. Worker replied to ping, and logs showed Beat sending the expiry task at one-minute intervals and Worker succeeding with no due rows. Critical source hashes for checkout, inventory and settings matched across workspace, web, worker and Beat. `docker compose config --quiet` exited 0. DB and media/static volumes are declared; Redis is not configured as a durable business-data source, but broker interruption can affect delivery. Web health only checks TCP. Worker/Beat do not have restart policies/healthchecks or singleton leadership across deployments. Nginx binds via localhost and configures a body limit; log output is local without verified external collection. The sample leaves secrets blank and includes the reservation setting; actual `.env` is mode 600 and ignored. No secret values were printed, and source history/secret-manager rotation was not audited.

## 15. Pre-payment architecture risks

1. **Initiation.** Persist a PaymentAttempt keyed by order and an idempotency key, with exact decimal amount/currency and deadline. Create or return the same attempt after an authorized request. Store unique gateway transaction identifiers tied to the merchant/provider and attempt. Do not hold inventory locks across network calls.
2. **Callbacks.** Authenticate signatures using the gateway's exact representation and replay controls, verify settlement with the provider as required, then check merchant, transaction, amount/currency and order match. Treat browser redirects as presentation only. Persist and deduplicate provider events separately from initiation idempotency.
3. **Atomic handling.** For an independently verified eligible success, begin one DB transaction. Lock the order before reservations and obtain any product locks in ascending ID. Recheck payment-attempt state and current reservation deadline, consume each matching active hold once, persist the verified payment and set order paid in the same transaction. Stock was already deducted at reservation; consumption must only close the hold. Duplicate callbacks should return the recorded result without consuming or charging again.
4. **Late success or mismatch.** If reservations have expired, been cancelled or already released, store a distinct received-but-unallocated payment outcome and route it for refund or manual reconciliation. Do not allocate released stock implicitly. Any approved reacquisition is a separate, explicitly locked availability check with an auditable policy. Compare provider event time, verification time and database deadline using a documented cutoff policy.
5. **Failure and timeouts.** Define whether failed or abandoned attempts release immediately or allow retry until reservation expiry. Serialize release with callback processing. Persist timeout and duplicate-event outcomes. Refunds require idempotent external requests and reconciliation jobs; stock restoration must follow an approved fulfillment/return policy rather than blindly following a financial refund.
6. **Reconciliation.** Compare provider settlements and refunds with PaymentAttempt states, inventory ledger entries and order totals. Alert on missing callbacks, expired-but-paid, duplicate charges, amount mismatches and orphaned transactions. A signed verified payment flow, refunds and reconciliation are not applicable to current validation.

## 17. Items not tested

Production TLS/certificates, policy provisioning against production credentials, duplicated Beat across hosts, forced Redis/DB outage, worker crash at commit, long-running lock contention, malicious third-party calls, data restore, populated migration or stock reconciliation, large catalog benchmarks, physical historical image retention, full cross-role/endpoint permission matrix and direct edge HTTP for docs. ## 18. Recommended remediation priority

1. Remove shared database superuser access from app processes and protect legacy absolute adjustment against stale writes.
2. Define stock reconciliation, restrict bypass paths, and make write-side idempotency explicit across checkout and inventory adjustments.
3. Expose deadline-aware order eligibility, add robust task supervision/monitoring, and run PostgreSQL failure and representative concurrency tests.
4. Approve the payment state-machine and late-success policy before integration, then test signed event replay and cancellation/expiry races in a separate phase.
5. Complete API error documentation, audit metadata policy and historical media retention.

## 19. Final readiness assessment

**READY AFTER FIXES.** Phase 1 behavior is repeatably testable on the current stack, but least-privilege deployment, stale-write protection and operational evidence are required for production. The report defines prerequisites for payment integration development; it does not approve that phase or certify the current payment architecture. No remediation was applied.
