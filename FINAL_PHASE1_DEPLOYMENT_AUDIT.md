## Independent inventory write-path audit

Searched application Python, migrations and tests for stock assignments,
inventory mutation functions, ORM updates and bulk writes. The supported
catalog API creates initial inventory via the service, and product PATCH
calls `orders/inventory.py:adjust_available` when stock is supplied. Django
admin makes existing stock read-only, reloads current stock under its row lock
on non-stock edits, and records initial stock in the same transaction on
creation. Cart edits read stock under a lock. Checkout locks product rows and
reserves inventory; cancellation and expiration release it through the
inventory service. The Celery task calls the expiration service. No alternate
stock mutation endpoint was found.

The absolute adjustment service compares the latest ProductChange revision
after taking the product lock, then computes the delta and writes the stock,
movement and audit together. A stale target returns 409. Signed delta and UUID
retry support remain. Existing regression tests cover stale adjustment after
reservation, competing absolute adjustments, unchanged balance on a stale
request, recorded delta, positive and negative constraints, and same-product
UUID replay. PostgreSQL's non-negative stock constraint remains in force.
UUID scope is still per product. Fixture code and historic migration code
contain inventory values. Raw SQL and unrestricted ORM maintenance writes can
still bypass the service ledger; this is the documented operational limitation,
rather than a discovered application API bypass. No application changes were
necessary for this audit.

recommendations. Live `manage.py check` reported no issues.
`makemigrations --check --dry-run` returned `No changes detected`.
`spectacular --validate --fail-on-warn` exited successfully.

Live HTTP probes reached Gunicorn inside the actual Web container:

- `/api/docs/`, `/api/schema/`, `/api/redoc/`, `/api/v1/products/` returned 200.
- `/health/` returned 404. The configured Compose TCP/database healthcheck
  reported healthy. There is no dedicated HTTP health route.
- Product detail with a nonexistent slug returned 404; no products existed
  for a live success probe.
- Profile, cart, addresses, orders, admin orders and admin ledger returned 401
  for unauthenticated probes. Authenticated CRUD and order checkout/list/cancel
  were exercised through the isolated integration suite, not by adding users,
  products or orders to the existing database.
