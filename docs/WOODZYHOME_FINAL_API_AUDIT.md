# ممیزی نهایی اتصال WoodZyHome

مبنای مقایسه [گزارش اتصال](WOODZYHOME_API_INTEGRATION.md) در Commit `4666e72` و قرارداد OpenAPI است. جدول هر ۲۰ عملیات را جداگانه بررسی می‌کند. مسیرها نسبت به `/api/v1/` نوشته شده‌اند.

| عملیات | علت نبود فراخوانی و پوشش موجود | نقص و تصمیم فرانت‌اند |
|---|---|---|
| `GET addresses/{id}/` | فهرست `GET addresses/` دادهٔ فرم آدرس را دارد؛ ویرایش با PATCH انجام می‌شود. | نقص کاربری ندارد؛ GET دوم لازم نیست. |
| `GET admin/audit-logs/{id}/` | جدول ممیزی از فهرست همان Serializer خوانده می‌شود. | نقص مدیریتی ندارد؛ صفحهٔ جزئیات مستقل در دامنه نیست. |
| `GET admin/categories/{id}/` | فهرست دسته‌ها دادهٔ فرم ویرایش را می‌دهد. | نقص مدیریتی ندارد؛ فراخوانی دوم لازم نیست. |
| `DELETE admin/categories/{id}/` | فرم مدیر وضعیت فعال را با PATCH کنترل می‌کند. حذف فیزیکی رفتار جداگانه‌ای دارد و آرشیو معنای آن را ندارد. | حذف فیزیکی در UI در دسترس نیست. برای انتشار این مرحله لازم نیست؛ عملیات معمول خروج از کاتالوگ با غیرفعال‌سازی انجام می‌شود. |
| `POST admin/payments/{id}/refunds/` | UI فهرست تراکنش و مغایرت دارد. این API فقط درخواست بازپرداخت ایجاد می‌کند و گردش واقعی بازپرداخت و تأیید درگاه را کامل نمی‌کند. | نقص عملیاتی برای فروش واقعی. اتصال تولید همراه با Provider رسمی، ردیابی درخواست و تطبیق نهایی لازم است. در این مرحله فرم تولید اضافه نشد. |
| `PATCH admin/payments/{id}/refunds/{refund_id}/simulate/` | API مخصوص بازپرداخت Mock است؛ پوشش از آزمون‌های بک‌اند می‌آید. | قابلیت کاربر یا مدیر تولید نیست؛ به UI تولید وصل نشود. |
| `GET admin/product-history/{id}/` | فهرست تاریخچهٔ فیلترشده با محصول، قیمت و موجودی رکوردها را برمی‌گرداند. | نقص مدیریتی ندارد؛ جزئیات جدا لازم نیست. |
| `GET admin/product-images/{id}/` | فهرست گالری اطلاعات لازم را برای PATCH یا DELETE می‌دهد. | نقص مدیریتی ندارد؛ GET دوم لازم نیست. |
| `DELETE admin/products/{id}/` | سرویس حذف فیزیکی محصول را رد می‌کند تا URL و تاریخچه حفظ شود؛ ویرایشگر غیرفعال‌سازی دارد. | عملیات عمداً ممنوع است؛ دکمهٔ حذف اضافه نشود. |
| `GET admin/ranking-weights/{id}/` | فرم وزن‌ها از فهرست و ویرایش با PATCH استفاده می‌کند. | نقص مدیریتی ندارد؛ GET دوم لازم نیست. |
| `GET admin/reviews/{id}/` | فهرست تعدیل، متن و پاسخ را برمی‌گرداند و PATCH و POST پاسخ متصل‌اند. | نقص مدیریتی ندارد؛ صفحهٔ مستقل لازم نیست. |
| `GET admin/seo/{id}/` | فرم رکورد صحیح را از فهرست فیلترشدهٔ SEO دریافت می‌کند. | نقص مدیریتی ندارد؛ GET دوم لازم نیست. |
| `DELETE admin/seo/{id}/` | فرم SEO ایجاد و ویرایش دارد. پاک‌کردن فیلدها فقط بخشی از نقش حذف رکورد را پوشش می‌دهد. | حذف کامل تنظیمات در UI وجود ندارد. برای فرایند معمول ویرایش ضروری نیست؛ افزودن آن به یک جریان تأییدشدهٔ بازنشانی موکول است. |
| `GET admin/users/{id}/` | فهرست مدیریتی دادهٔ نمایش و فعال/غیرفعال‌کردن را دارد. | نقص مدیریتی ندارد؛ GET دوم لازم نیست. |
| `GET dashboard/favorites/` | داشبورد فقط جمع و پیوند داشت و فهرست مستقل علاقه‌مندی خارج از آن بود. | نقص نمایش داشبورد؛ فهرست اخیر و پیوند محصول اضافه شد. |
| `GET payments/{id}/` | صفحهٔ نتیجه از `GET payments/{id}/status/` استفاده می‌کند که در URLConf به همان view وصل است. | هم‌پوشانی قراردادی؛ GET دوم لازم نیست. |
| `POST payments/callback/{provider}/` | webhook از طرف Provider فراخوانی و در سرور اعتبارسنجی می‌شود؛ رابط وضعیت را از API استعلام می‌کند. | مسیر داخلی ادغام است؛ UI آن را فراخوانی نکند. |
| `GET payments/mock/{id}/simulate/` | view از GET جزئیات ارث می‌برد؛ صفحهٔ پرداخت با status endpoint داده می‌گیرد و برای سناریو POST دارد. | مسیر آزمایشی و هم‌پوشان؛ فراخوانی جدا لازم نیست. |
| `GET products/most-favorited/` | بخش محبوب‌ها امتیاز ترکیبی دارد و معادل رتبهٔ ذخیره‌سازی نیست. | نقص نمایش فروشگاه؛ بخش جدا با شمارش غیرصفر اضافه شد. |
| `GET search/recent/` | تاریخچه در داشبورد بود و صفحهٔ جست‌وجو فقط عبارت‌های محبوب را نشان می‌داد. | نقص کاربری جست‌وجو؛ پیوند جست‌وجوهای اخیر خود کاربر اضافه شد و درخواست شخصی کش مشترک ندارد. |

پس از این تغییرات، **۱۰۲ از ۱۱۹ عملیات** فراخوانی رابط دارند. ۱۷ مورد باقی‌مانده شامل مسیرهای خواندن هم‌پوشان، مسیرهای تست یا داخلی، یا گردش‌های مدیریتی خارج از انتشار فعلی است. این عدد پوشش آزمون همهٔ عملیات نیست.

## تنظیمات Production

- در محیط **سرور Next.js** مقدار `DJANGO_API_URL=https://api.example.com/api/v1` یا نشانی خصوصی مسیریابی‌شده را قرار دهید. در شبکهٔ کانتینری `localhost` یعنی همان کانتینر Next، مگر اینکه هر دو سرویس واقعاً در یک network namespace اجرا شوند. hostname درخواست باید در `DJANGO_ALLOWED_HOSTS` مجاز باشد. پس از تغییر env، فرایند Next را راه‌اندازی مجدد کنید.
- اگر رسانهٔ Django با نام خصوصی سریال می‌شود، `DJANGO_MEDIA_URL=https://api.example.com/media` را با مسیر HTTPS قابل دسترس مرورگر تنظیم کنید. `STORE_CURRENCY` را با Django هماهنگ نگه دارید. `WOODZY_SHOWCASE=0` و `WOODZY_TEST_PAYMENTS=0` در Production ضروری‌اند.
- در Django مقادیر `DJANGO_DEBUG=0`، `SITE_URL`، `DJANGO_ALLOWED_HOSTS`، `CORS_ALLOWED_ORIGINS`، `CSRF_TRUSTED_ORIGINS` و سیاست کوکی و HTTPS را با ingress هماهنگ کنید. `SECURE_COOKIES=1` و `SECURE_SSL_REDIRECT=1` نیاز به تنظیم صحیح HTTPS در پراکسی دارند. پیش از اعتماد به هدرهای پراکسی، بازنویسی و منبعشان باید در ingress کنترل شود. کوکی‌های JWT سرور Next در Production به HTTPS نیاز دارند.
- از PostgreSQL و Redis خصوصی با دسترسی محدود استفاده کنید. Migration را با نقش مجزای migrations اجرا کنید و Worker/Beat را با تنظیمات همان محیط اجرا کنید. Secretهای Django، دیتابیس، ایمیل و پرداخت را در محیط سرور نگه دارید. `PAYMENT_MODE=production` و `PAYMENT_MOCK_ENABLED=false` را تنظیم کنید.
- بازیابی و خبرنامه به SMTP واقعی و Worker نیاز دارند. فعال‌سازی یا تأیید پرداخت و بازپرداخت واقعی به Provider معتبر، قرارداد و مسیر callback تأییدشده وابسته است. پایان موفق تست Mock به معنای امکان دریافت پول واقعی نیست.

## معیار انتشار

آمادگی Push کد و آمادگی بهره‌برداری عمومی دو تصمیم مختلف‌اند. نتیجهٔ اجرای همین مرحله در بخش آزمون درج می‌شود. فروش عمومی با پرداخت واقعی، SMTP و ingress مقصد تا زمان تأیید آن سرویس‌ها آماده نیست.

## نتیجهٔ آزمون نهایی

| بررسی | نتیجه |
|---|---|
| Django `manage.py test --keepdb --noinput` | ۱۲۹ آزمون موفق روی PostgreSQL 17.12 با Redis ایزوله |
| Playwright `node --test --test-reporter=tap tests/storefront.test.mjs` | ۳۶ موفق، ۰ خطا و ۰ ردشده؛ خروجی خود آزمون ۰ |
| مسیرها | ۲۷ صفحه با دادهٔ Django و هفت viewport؛ گردش‌های مستقل حساب، فروشگاه، خرید آزمایشی و مدیریت نیز اجرا شدند |
| اتصال‌های تازه | ثبت علاقه‌مندی و مشاهده در داشبورد، ثبت جست‌وجوی کاربر و نمایش در تاریخچهٔ جست‌وجو در مرورگر بررسی شدند |
| TypeScript و Build | موفق روی Next.js 16.4.6 |
| OpenAPI | ۹۴ مسیر، ۱۱۹ عملیات نسخهٔ v1، `spectacular --validate` موفق |
| سازگاری استقرار | `makemigrations --check --dry-run`، اعتبارسنجی Compose و `check --deploy --fail-level WARNING` با مقادیر نمونه موفق |

در نخستین اجرای آزمون مرورگر، selector تاریخچه به ظرف عنوان محدود بود. پس از اصلاح selector و آماده‌سازی حالت علاقه‌مندی برای اجرای تکراری، مجموعه کامل موفق شد. ظرفیت تولید از این تست نتیجه‌گیری نمی‌شود؛ محیط مرورگر از سقف نرخ مخصوص آزمون استفاده کرد.

**آمادهٔ بازبینی و Push کد پس از تأیید مالک است.** استقرار عمومی فروشگاه با پرداخت واقعی هنوز به تنظیم و تأیید Provider و بازپرداخت، SMTP و HTTPS/ingress مقصد نیاز دارد. هیچ Push انجام نشد.
